# 学习文档写作与图解标准（AI 自用总纲）

> **一句话原则**：降低理解门槛，不降低技术含量；每个断言可追到 `文件:行`，每张图回答一个学习问题。
>
> **本页是唯一事实源。** 原 `nccl/qa-writing-standards.md` 与 `ai/tools/knowledge-diagram-writing-standard.md` 已并入本页，只留指针。新会话接到"写/改学习文档"类任务，读这一篇即可对齐，不必重新摸索。

---

## 0. 先做的第一件事：判定文档类型

**不同类型的验收标准差一个量级，写之前必须先定型。** 判错型的典型后果：把移植级长文写成概览（读者看完仍不会写代码），或把 QA 页写成长文（问题被埋在三千行里）。

| 类型 | 一句话目标 | 深度下限 | 长度 | 图解 | 验收问句 |
|---|---|---|---|---|---|
| **A. 移植级长文** | 看完能从零重写一套等价实现 | **字节级 / 位级**：格式布局、魔数、公式推导、对齐规则全给 | 不限，单篇（本次样本 3300 行） | 密集，按章配图（本次 16 张） | "照着这篇能写出能跑的实现吗？" |
| **B. 端到端讲解** | 看完能说清一条链路怎么走通 | 主体函数级 + 关键数据结构字段 | 800–2000 行 | 全景图 + 每阶段一张 | "能复述一次调用从头到尾经过谁吗？" |
| **C. QA 页** | 精准回答具体提问，可追加 | 与问题同深度，宁深不浅；边界要立起来 | 每条 100–400 行 | 按需，只给"讲不清才需要图"的那几张 | "这一条把提问者的误解拆掉了吗？" |
| **D. 索引 / 导航页** | 三十秒内把人送到正确的页 | 只要路由 + 一句话定位，**不要**搬正文 | 越短越好 | 最多一张全局地图 | "陌生人能靠它找到东西吗？" |
| **E. 标准 / 规范页** | 让下一个人（含 AI）不重复踩坑 | 每条规则附"为什么"与踩坑实例 | 中等 | 少或无 | "照做能避开原来那个坑吗？" |

判型的两个追问：

1. **读者看完要能"做"什么？** 能重写实现 → A；能讲清流程 → B；解开一个疑惑 → C。
2. **是新知识还是路由？** 路由 → D，别写成长文。

> ⚠️ **类型 A 的隐含要求最容易漏**：既然目标是"能重写"，就必须写**格式规格**（偏移、位宽、对齐、魔数值）而不只是"调用了哪个函数"。函数名能抄，字节布局抄不出来——它只能来自实测。

## 1. 知识深度标准（全类型通用）

1. **落到 struct 字段级 + `文件:行`。** "bootstrap 有个环"不合格；合格写法："环的实体是 `bootstrapRing_t.socket.send/recv` 两条常驻 TCP（`bootstrap.cc:490`），没有 prevRank/nextRank 字段"。关键断言给行号，必要时引几行带注释的代码块。
2. **区分"源码确认"与"推断"，不许混写。** 源码没写明设计动机时，推断要显式标注。
3. **两侧都要覆盖。** host / device、UMD / KMD、注册期 / 运行期——数据结构常有双份镜像，哪些字段拷过去、哪些是单侧的，必须交代。只讲一侧算漏一半。
4. **讲 why，不只讲 what。** 给设计动机与替代方案对比（例："为什么 bootstrap 把拓扑存成连接、channel 把拓扑存成数据"）。
5. **主动做边界澄清。** 提问往往隐含一个以偏概全的前提，回答要把边界立起来，而不是顺着错误前提答。
6. **同名概念必须显式对比。** 一个栈里常有多个同名不同物（两个"环"、两处"prev/next"、wrapper 与 bundle 都被叫"fatbin"）；讲其中一个时主动与另一个对照，否则读者必然混淆。
7. **死代码必须标注出来。** 移植时照抄死代码是纯浪费。判定标准是**全仓库无调用点**，不是"看起来没用"。本次抓到的实例：`kernelCodeHandle_` 只写不读（无 `KernelCodeHandle()` 调用点）、整套 ISA 字符串解析在 COMGR 路径下从不执行、`WITH_COMPILER_LIB` 分支全仓库从未定义。
8. **"本文未验证事项"必须成节。** 明确列出没覆盖的部分（未采集的运行时数值、无源码的闭源库内部、未走到的代码路径）。**诚实标注不降低文档价值，含糊其辞才会。**
9. **移植级长文必须有陷阱清单。** 按"抄这份代码时会被坑到"排序，每条给 `踩法 / 后果 / 正确做法` 三列。本次积累到 22 条。
10. **新知识必须回灌对应正文，不能只留在 QA 页。** QA 里挖出的新事实要外科手术式补进相关章节，并留交叉链接。
11. **发现既有内容与源码冲突时当场修正**，并在提交信息里说明。

## 2. 证据分级（画图与写断言前先归档）

| 结论类型 | 权威来源 | 状态 | 可否写成确定事实 |
|---|---|---|---|
| 软件调用、字段赋值 | 当前源码快照（记下 commit） | source-confirmed | 可以 |
| section / symbol / 指令布局、结构体尺寸 | 实际编译 + `readelf` / `objdump` / `offsetof` 探针 | artifact-confirmed | 可以 |
| 模块职责、调度规则 | 当前设计文档 / MAS | document-confirmed | 可以，标明文档边界 |
| 闭源库内部、保密 RTL | 未获得 | unverified | **不得臆测** |
| 上下文补出的解释 | 推断 | inferred | 必须显式标注 |

**强制顺序**：`读真实来源 → 记录证据与未知项 → 定结论 → 设计布局 → 绘制`。禁止先凭经验画图、再用源码为成图找解释。

**本地源码副本必须与远端校验一致**（逐文件 md5），否则所有行号引用都不可信。本次做法：拉一份副本到临时目录，与远端 `d32f4a9d` 逐文件比对后再引用。

**实测优先于文档。** 本次最有价值的一条结论来自"头文件与实现不符"：`iterate_map_metadata` 头文件写"回调返回非 SUCCESS 则中止"，探针实测**返回值被完全忽略**，反汇编（`call *%rbp` 后无 `test %eax`）与上游源码三重印证。若只读头文件就写文档，会得出与真实行为相反的结论。

## 3. 写作风格

### 3.1 章节与小节

- **以符号命名的小节，开头必须有一两句"这个函数/结构干什么"**，然后才是代码块。反例是标题后直接甩源码——读者得先读完实现才知道目的。（本次为两篇长文的 46 个小节补了这个开场；这是用户明确要求。）
  - 不合格：`### 4.2 setBinary` 后紧跟 30 行代码。
  - 合格：`**作用**：把 code object 字节交给 ClBinary 保存，并读 ELF 头的 e_type 判定这份二进制处于哪个编译阶段。这一判定决定后面走不走编译管线。`
- 函数名不能孤立出现，旁边给一句职责：不写裸 `Thunk_CreateEngine()`，写 `Thunk_CreateEngine()`——向 KMD 请求建立可调度队列，取得后续 doorbell 提交所需能力。
- 长文开头给**术语与血缘对照表**（本栈名 ↔ 上游原型名）。移植改名的项目里，这张表能省掉读者一半困惑。
- 移植级长文的固定骨架：`全景 → 格式规格（字节级）→ 各阶段逐函数 → 移植清单（分区 + 最小路径 + 陷阱）→ 附录（取证命令 + 原始 dump + 源码地图 + 常量速查）`。
- 附录里放**可复现的取证命令**。别人重跑一遍就能验证，这是长文可信度的地基。

### 3.2 QA 页

- 一问一条，标题写**用户原话**（便于日后按记忆检索），下面才是结构化回答。
- 同主题追问**并入已有条目**成为新小节，不散落成孤立小条；条目内互引用"见二/见三"，不用会因合并失效的 Q 号。
- 每条回答的推荐结构：`一句话结论 → 详细展开 → 边界/易混淆点 → 证据（文件:行、实测）→ 延伸阅读链接`。
- **先把提问里的错误前提点出来**，再回答。

### 3.3 语言

- UTF-8 中文正文；代码、标识符、路径、命令、技术术语保留原文。
- 结论先行，不要铺垫；能用表格的不用段落堆叠。
- 不确定就写"未验证"，不要用"应该 / 大概 / 估计"糊过去。

## 4. 图解

### 4.1 三级符号策略

| 层级 | 内容 | 处理 |
|---|---|---|
| **L1 系统骨架** | UMD / KMD / CP、模块与分层 | 必须保留，建立系统位置 |
| **L2 主体入口** | 主体函数、ioctl、包类型、接口 | 按需保留，**紧跟一句自然语言职责** |
| **L3 内部实现** | 内部容器、局部变量、状态字段、辅助函数、寄存器位域 | 主图不展开，下沉正文或深入页 |

判据：删掉这个符号后，读者还能说清"谁调用谁、为什么、产生什么结果"吗？不能则保留；只影响函数内部实现则下沉。

两个极端都不许：只剩模块名和箭头（看不出真实调用框架）；连续罗列内部函数字段（用符号数量代替解释）。

> "面向新人可懂"= 补上下文、输入输出、设计原因；**不等于**删技术主线。

### 4.2 流程门禁（本次被用户点名的地方，必须照做）

1. **写 Diagram Brief** —— 复杂图 / 正式 wiki 图 / 多图任务一律先填，模板见 skill 的 `assets/diagram-brief-template.md`，填完跑：
   `node /root/.claude/skills/technical-diagram-generator/scripts/check-diagram-brief.cjs <brief.md>`
   字段缺失、留占位符、没有证据边界 → 不得进入绘图。
2. **试点审批** —— 两张及以上正式图、指定风格、整篇重构，必须先交**一张最具代表性的图 + 一个使用它的完整正文小节**，等用户批准。批准后把画布、字号、配色语义、卡片结构、箭头风格、信息密度记为本任务视觉基线。
3. 批量制作 → 4. 自动 lint → 5. 逐张目检 → 6. 发布并核对链接。

> 🩸 **踩坑记录**：本次第一轮虽然调用了 `technical-diagram-generator`，却跳过了 Brief、跳过了审批门禁（自己看了第一张就继续批量）、也没跑三个验证脚本，被用户直接指出。**"调用了 skill" ≠ "按 skill 流程执行"**，门禁是流程的一部分而不是建议。

### 4.3 工具选型

| 场景 | 选择 |
|---|---|
| 学习讲解、正式 wiki 图 | **手写 SVG**（首选，信息密度与排版可控） |
| 稠密确定性图 | Graphviz DOT |
| 行内简单流程 | Mermaid |

**Graphviz 与 layout linter 系统性不兼容**：linter 把 `<path>` 的 `d` 里每个数字当折线顶点（含贝塞尔控制点），而 Graphviz 的节点/表格边框都是 `<path>`，于是必然大量告警。已客观核实：vault 里 17 张既有 Graphviz SVG **全部**命中 12–20 处。手写 SVG 可真正做到零告警。**别花时间去"修" Graphviz 的告警，换工具或明确记为已知误报。**

**手写 SVG（svgkit）不能"直接生成"drawio，两条流水线不互通（2026-08-12 实测）。** 三条路径逐一验证过：

1. **svgkit 本身零 drawio 感知**——`svgkit.py` 全文对 `drawio`/`mxCell`/`mxGraphModel` 零命中，它只吐纯 SVG 字符串。
2. **把整张 SVG 当图片嵌进 `.drawio`**（`shape=image` + base64 data URI）是唯一可能的"关联"方式，但实测在本机 headless `xvfb-run drawio` 环境下**导出失败**（渲成"图片损坏"占位符）；即便调通，换来的也只是一张**不可编辑的贴图**——在 drawio 编辑器里点不进去改任何文字或线条，不构成"生成 drawio 图解"。
3. **`technical-diagram-generator` 的 drawio 能力不是转换器**：`drawiokit.py` 直接生成原生 `mxCell` 节点——全仓库搜不到任何"解析既有 SVG 再转成 drawio 节点"的代码。

**结论**：SVG 与 drawio 是两条独立维护的表达，没有"先出 SVG 再转 drawio"的捷径。要拿到内容等价、真正可编辑的 drawio 版本，唯一办法是把内容**重新用 `drawiokit.py` 描述一遍**，让它原生生成 `mxCell`；drawiokit 的卡片模板（badge/title/body/divider/status）比早期的三段式宽，但仍装不下 svgkit 那种自由坐标的信息密度（实测对照见 `g1-nine-stages` 的"① 编译期打包"卡：同一份内容在 TDG 下语义分层全部塌缩成一段无差别文字）。

### 4.4 手写 SVG：几何约束（硬性）

这些数值是踩出来的，直接用现成生成器 `scripts/svgkit.py`（在 skill 里）而不要手算：

- 基线间距 ≥ `1.35 × font-size`，硬底 `1.2 × max(前, 当前)`。
- 卡内文字底部净空 ≥ 10px（从 `baseline + 0.25×fs` 起算）。
- 文字宽度超出卡片可用宽度 → **断言失败**（CJK 按 1.0em、其余按 0.55em 估宽）。
- 分隔线：上方留 26px、下方留 48px。理由：文本框下沿 = `baseline+16`，下一行文本框上沿 = `baseline−(1.35fs+8)`。
- **表格不用行分隔线，用斑马纹**——行线必然落进文字的 16px 净空区。
- 箭头 marker 14px `userSpaceOnUse`；短段的 marker 不超过段长 65%。

- **内存布局一律竖排、低地址在上**，用 `Doc.vmap()`（2026-08-19 加进 svgkit）。理由：地址轴天然是纵向的；横排既不合阅读习惯，又受画布宽度限制装不下多少段。`vmap()` 每段高 `max(minh, 权重占比 × 总高)`，`minh` 保证极小的段仍放得下标签，返回 `[(段名, (顶部y, 底部y))]` 供调用方把箭头挂到具体段上；标签超宽会 append 进 `problems`，是真门。
  多个布局**并列成若干竖列**比堆成若干横带更强：同一个段可以横向对照，跨列箭头还能直接画出"某段被搬到了别处"。实测收益——把 `gotDataDevMemory_` 的四个布局并列后，"列③因顶部多一块 GOT 而整体下移，下移高度恰好等于 `data_offset`" 这件事从需要文字解释变成了肉眼可见。
- **别在 scratchpad 留 svgkit 私有副本**，直接 `sys.path` 指向 skill 里的 canonical 版。svgkit 已把几何常量集中到 `assets/layout-constants.json`（生成器与两个 linter 共用），私有副本正是当初生成器与 linter 漂移的原因。

> 🩸 **踩坑记录（系统性）**：卡片测高探针**漏算了 tag 徽章的 60px**（42 高 + 18 间距），导致所有行高偏短，某张图的箭头起点落进了卡片内部。修法是提供唯一的 `measure()` 入口，**始终按"有徽章"计**，让探针与绘制不可能不一致。教训：凡"算尺寸"与"画元素"是两段代码，就必须共用同一函数，否则迟早不一致。

### 4.5 硬性禁忌

- **SVG 文本里禁 emoji**（渲染成乱码方块）。
- **SVG 文本里禁 Markdown 标记**（`**加粗**` 会原样渲染出星号）；强调用 `font-weight="700"` 或换色。
- XML 转义：`->` 写 `-&gt;`，`&` 必须转义。**`<desc>` 里同样**——未转义的 `&` 会让 sharp 报 `xmlParseEntityRef: no name` 拒渲整张图。
- **元素必须分层书写**，不许按空间区域顺序写。手写 SVG 的 z-order 完全由书写顺序决定（后写盖先写），严格按 `① 背景/分区矩形 → ② 全部连线 → ③ 全部节点框 → ④ 文字/带底色标注` 四组，每组加 `<!-- layer N -->` 注释；**跨区域连线一律进第②层**。反例：按"从上到下逐块"写，后铺的不透明分区背景把先画的跨域连线整段盖住——源码坐标完全正确，渲染出来却断了。
  - 🩸 **连线的"文字标签"必须进第④层，不能跟着连线留在第②层**（2026-08-19 又栽一次）。把跨列箭头的标签和箭头一起画在第②层，后绘的不透明色块盖掉了标签前半截，右对齐的 `每次 launch` / `device→device` 渲染出来只剩 `launch` / `device` 两个词——**自检与 lint 都不报**（几何合法、连线也没被判定压字），只有逐张目检 + 裁切放大才看得出。两条修法同时用：① 标签排进第④层（色块之后）；② 连线与标签都只走"列间空道"，从根上不与色块重叠。

### 4.6 内容设计

- **一图一个学习问题**；全景图除外，但要区分"一次性初始化 / 每次调用主路径 / 完成反馈"。
- **不做只是裁剪或重复另一张图的新图**——要么合并，要么给出不同的学习问题。QA 页配图尤其要检查是否与长文既有图重复：同一对象换**视角**（职责归属、生命周期、为什么这样设计）才算新图。
- 普通阶段图结构：`本阶段解决的问题 → 输入 → 主体动作/函数 → 输出 → 为什么需要`。
- 箭头必须表达调用 / 数据 / 查表 / 完成反馈之一，**不能只作装饰**；颜色只编码语义，同一含义跨图保持同色。
- 示例要跨图一致（同一个 `add1`、同一组 rank 划分），别每张图换套数据。

### 4.7 验证

```bash
node /root/.claude/skills/technical-diagram-generator/scripts/lint-svg-text-overlap.cjs <svg>
node /root/.claude/skills/technical-diagram-generator/scripts/render-png.mjs <svg 或目录> [png目录]
node /root/.claude/skills/technical-diagram-generator/scripts/verify-wiki-diagrams.cjs page.md index.md hot.md log.md
```

目检（`Read` 工具直接看 PNG）必查项：

- 箭头方向与完整性；**连线闭合性是独立必查项**——逐条确认两端压在框边、中间无断点，**必须裁剪放大每个连接密集区**，整图缩略图下断点几乎不可见，且看图时容易有"我画对了"的确认偏差。看图时反过来问"哪条线是断的、哪个框是孤立的"。
- 有背景分区（band/panel）的图**必做半透明自检**：临时把背景矩形改 `fill-opacity="0.3"` 渲一版，被遮挡的连线立刻现形。这是抓 z-order 遮挡的确定性手段，lint 查不出来。
- 文字在卡内不压边、不重叠；页宽下能懂分层与主路径，100% 下能读到函数名与公式。
- 多图任务出 contact sheet，检查字号/配色/密度有没有漂移。
- **图例必须与图内容一致**——本次抓到两处"图例描述了图里并不存在的箭头"。
- 改完 SVG **必须重渲并重新拷 PNG**（只改源不重渲 = 正文里还是旧图）。

### 4.8 文件与引用规则

- ASCII 文件名。PNG 放 `_attachments/<domain>/<topic>/`，SVG 源同名放其 `src/`。
- 正文引用格式：**两行 + 中间一个空行**
  1. 图片嵌入行：`!` + `[详尽中文 alt 文本]` + `(相对路径/gNN-name.png)`
  2. 空行
  3. 源文件行：`> 图解源文件：` + 指向 `src/gNN-name.svg` 的行内链接（注明 hand-authored SVG）

  实例见 [UMD qa-log](<../../grace/umd/qa-log.md>) 每张图下方两行。

- alt 文本要把信息量写全（同时充当无图环境的降级说明）。
- 图内交叉引用用**当前有效**的名字（合并后的 Q 号会失效）。

## 5. Review：怎么真的查出错

**自查靠脚本，不靠重读。** 本次一轮 review 抓出 5 处真错，全部来自机械核验而非通读：

1. **引用核验**：脚本提取全文所有 `文件:行`（本次 235 处），逐条检查文件存在、行号未越界。
2. **代码比对**：提取全文引用的代码块（本次 705 行），去空白后与源码逐行比对。
3. **结构 lint**：代码围栏配平、标题层级连续、`---` 前有空行（否则被解析成 setext H2）。
4. **反向查证关键断言**：对"X 用于 Y"这类因果断言，反查 X 的**全部调用点**。本次由此发现 `kernelCodeHandle_` 根本没有读取点，原先写的用途是错的。
5. **自相矛盾扫描**：同一节里的代码块与分析文字是否一致（本次抓到代码块漏了 `static_cast<uint32_t>`，恰好与同节的溢出分析相反）。
6. **数量核对**：文中所有"N 项/N 条"的计数重新数一遍（本次把隐藏参数 24 项纠为 22 项，图解同步改）。

> 结论性断言（含"做不到 / 不可能"）同样需要证据。**若证据与结论冲突，错的是结论，不是证据。**

## 7. 工具纪律（血泪，与项目 CLAUDE.md 一致）

- **一次只发一两个工具调用，发出即停、等真实返回；绝不自己续写工具结果。** 单条回复塞太多（长解释＋大段源码＋多调用）会超 max output 被截断，省略号即征兆，进而把幻觉续写的"成功回执"当真——曾因此连续误报落盘成功，实际磁盘为空。
- **改完必验，且用独立命令交叉确认。** Edit/Write 的 "updated successfully" 只是声明；改完立刻 `grep -c <标记> <file>`，再 `git status --short` 二次确认。**回执与磁盘不符时信磁盘。**
- 本机 shell 对中文 `echo`、多分号、`grep -n` 正则会输出重复/乱码；用最简单的单命令、纯 ASCII 参数。
- 提交只 `add` 自己的文件；提交前扫描密码未泄漏（`git diff --cached | grep -c -F "$SECRET"` 须为 0），**绝不回显密码值**。
- 声明"做完了"之前先跑独立读回；`git log --oneline -1` / `git ls-remote origin <branch>` 才算推送凭据。

## 8. 沉淀下来的固定结论

1. "新人可懂"靠解释与分层实现，不靠删技术主线。
2. 单图审批不足以锁定全文风格——必须同时审批一个正文小节。
3. `st_value` / `init_pc` 这类地址关系，必须先读源码、实编译、解析 section/symbol，再绘图。
4. 注册流程要画**注册表实例**（键是什么、值是什么、谁填谁读），不是堆内部类型名。
5. 三个软件层若只是全景图局部截图，应合并回全景图。
6. 移植文里"这段是死代码"和"这条契约与文档不符"往往是最高价值的两类结论——它们直接决定别人要不要抄。
7. 凡"算尺寸"与"画元素"分两段代码，必须共用同一函数。
8. 长文里的计数（图数、陷阱数、行数）会过期，改内容时顺手核对索引页里的数字。
